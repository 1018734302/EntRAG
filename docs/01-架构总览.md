# 01 · 架构总览

## 1. 技术选型

| 分层 | 选型 | 说明 |
|---|---|---|
| 后端框架 | Spring Boot 3.4.5 | |
| AI 抽象层 | Spring AI 1.0.0 | `ChatModel` / `EmbeddingModel` / `VectorStore` 统一抽象 |
| 对话模型 | Ollama `qwen3:4b`（推理型） | 本地运行，需关闭思考 |
| 嵌入模型 | Ollama `qwen3-embedding:4b` | **2560 维** |
| 向量库 | PostgreSQL 16 + pgvector 0.8.6 | 关系库 + 向量二合一 |
| 文档解析 | Apache Tika 2.x | PDF / Word / Markdown / TXT |
| 鉴权 | Spring Security + JWT | 无状态，多知识库租户隔离 |
| 前端 | Vue 3 + Vite 5 + TypeScript + Element Plus + Pinia | fetch-SSE 流式 |

## 3. 数据模型

| 表 | 归属 | 作用 |
|---|---|---|
| `users` | 业务 | 用户账号 |
| `knowledge_base` | 业务 | 知识库（归属用户） |
| `doc_meta` | 业务 | 文档元数据：文件名、大小、**状态**、分块数、错误信息 |
| `vector_store` | Spring AI | 分块向量：`id` / `content` / `metadata(jsonb)` / `embedding vector(2560)` |

关键设计：**业务表与向量表在同一个 PostgreSQL 库**。好处见下。

## 4. 为什么用 PostgreSQL + pgvector，而不是 Milvus？

核心原因是 **RAG 需要"结构化 + 向量"混合查询**：

```java
// 向量相似度召回 + 按 kbId 过滤，同一条 SQL 完成
SearchRequest.builder()
        .query(question)
        .topK(topK * 2)
        .filterExpression(b.eq("kbId", String.valueOf(kbId)).build())
        .build();
```

- **混合查询**：权限/租户过滤与向量检索一次完成，不必"先召回再回业务库过滤"
- **一致性**：删文档要同时删元数据与向量，同库便于统一处理
- **运维成本**：私有化交付少一个组件，少一套部署/监控/备份
- **规模边界**：pgvector 适合千万级以内；上亿再考虑 Milvus

### 已踩到的硬约束（务必记住）

> **pgvector 的 HNSW 索引维度上限是 2000 维**，而 `qwen3-embedding:4b` 输出 **2560 维** → 建不了 HNSW。
> 当前配置为 `index-type: NONE`（精确检索）。选型时**必须先确认嵌入模型维度**。

## 5. 两条核心链路

- **离线入库（异步）**：上传 → 立即返回 taskId → 后台解析/分块/向量化 → 前端轮询进度
- **在线问答（流式）**：提问 → 向量召回 → 融合重排 → SSE 推引用 + 逐 token 生成
